# Ядро rvos — справочник

Это описание устройства, а не история разработки. Историю рассказывает
[README](../README.md): он идёт по стадиям и объясняет, почему что-то вышло
именно так. Здесь — как оно есть сейчас, по подсистемам, с числами и ссылками
на исходники.

Внутри работающей машины есть `cat /doc/kernel` — та же справка про системные
вызовы, но короче и по-английски, как и весь текст внутри машины. Этот документ
подробнее и охватывает то, чего там нет: трансляцию адресов, устройство задач,
правила рандеву.

**Границы предмета.** Ядро — то, что выполняется в S-режиме: `boot.S`,
`mstart.c`, `kmain.c`, `pmm.c`, `vm.c`, `task.c`, `ipc.c`, `trap.c`, `plic.c`,
`vfs.c`, `fdt.c`, `pci.c`, `doc.c`. Серверы (`srv_*.c`, `sh.c`, `srv_rsh.c`,
`net_ip.c`, `loader.c`) лежат в том же образе, но выполняются **в
пользовательском режиме** и ядром не являются. Они перечислены в разделе 9.

## 0. Что это

Учебная микроядерная операционная система для RISC-V. Собирается
`riscv64-unknown-elf-gcc`, работает на `qemu-system-riscv64 -machine virt`.

- **Архитектура** — rv64imac с `zicsr` и `zifencei`; ABI lp64, модель кода
  medany.
- **Трансляция адресов** — Sv39: 39-битный виртуальный адрес, три уровня
  таблиц.
- **Ядро в S-режиме.** M-режим используется ровно один раз, при загрузке, и
  только затем, чтобы уйти в S: `satp` в M-режиме игнорируется, то есть без
  этого перехода не было бы страничной памяти вовсе.
- **Всё остальное — в U-режиме.** Файловая система, консоль, сеть, оболочка,
  загрузчик программ — обычные непривилегированные задачи.
- **Единственный способ общения — сообщения.** Синхронное рандеву между
  задачами; ядро копирует байты между адресными пространствами.
- **Единственный способ именования — пути.** У каждой задачи своя таблица
  монтирования; путь разрешается в задачу-сервер и в имя, о котором её надо
  спросить.

```
        железо (QEMU virt)
              │
   M-режим    mstart.c     делегирование, PMP, Sstc → mret
              │
   S-режим    ядро         страницы, задачи, ловушки, сообщения, имена
              │
   U-режим    серверы      fs · console · proc · dev · net · null
              │            sh · rsh · loader
              │
   U-режим    программы    /BIN/*.ELF, загруженные с диска
```

Разница между сервером и программой — только в происхождении: сервер собран в
образ ядра и запущен при загрузке, программа прочитана с диска. Прав у них
одинаково: никаких.

## 1. Загрузка

### 1.1 `boot.S` — первые инструкции

QEMU входит по адресу загрузки на **каждом** харте, с `a0 = hartid` и
`a1 = адрес дерева устройств`.

```asm
    csrr    t0, mhartid
    bnez    t0, park              # вторичные харты: wfi навсегда
    mv      s0, a1                # дерево устройств — до очистки .bss
    ...очистка .bss...
    la      sp, __stack_top
    la      t0, dtb_pa
    sd      s0, 0(t0)             # запись после очистки, иначе обнулится
    call    mstart
```

Три вещи, каждая из которых важна:

- **Только харт 0 продолжает.** Остальные уходят в `wfi`; многоядерности в
  системе нет, и вся синхронизация отсутствует именно поэтому.
- **`.bss` чистится вручную.** Загрузчика, который сделал бы это, нет — ядро
  прыгает прямо в свой ELF.
- **Указатель на дерево устройств сохраняется в регистре, а записывается в
  память после очистки.** Запись до очистки была бы обнулена ею же.

### 1.2 `mstart.c` — единственный код в M-режиме

Сорок восемь строк, четыре обязанности. Забыть любую — значит заклинить
машину так, что отладить трудно.

| что | зачем |
|-----|-------|
| `mstatus.MPP = S`, `mepc = smain`, `mret` | собственно передача управления в S-режим |
| `medeleg = 0xffff`, `mideleg = 0xffff` | без делегирования любая ловушка S-режима поднимается в M, где обработчика уже нет |
| `pmpaddr0` на всю память, `pmpcfg0 = 0xf` | PMP по умолчанию запрещает S-режиму трогать что-либо; без настройки первая же инструкция после `mret` даёт сбой |
| `mcounteren = 0xffffffff` | разрешает `rdtime` из S-режима — на нём держится таймер |
| `menvcfg.STCE` (бит 63) | включает Sstc, то есть CSR `stimecmp` |

Последняя строка — не мелочь. `mtimecmp` в CLINT доступен только машинному
режиму, а машинное прерывание таймера **не делегируется**. Без Sstc у ядра в
S-режиме нет собственного таймера, и пришлось бы держать в M-режиме обработчик,
пересылающий каждый тик вручную.

### 1.3 `kmain.c` — порядок инициализации

Порядок не произволен; каждый шаг зависит от предыдущего.

1. **Очистка `.bss` серверов.** У каждого сервера свой участок данных (см.
   3.5), и `boot.S` чистит только `.bss` ядра.
2. **Дерево устройств** (`fdt_init`). До `vm_init`, потому что карта
   отображений строится по тому, что скажет плата — в частности, где окно
   конфигурации PCI.
3. **`pmm_init`** — арена свободных страниц от конца образа до `PMM_TOP`.
4. **`vm_init`** — таблица ядра и включение трансляции. С этого момента любой
   адрес виртуален.
5. **`pci_init`** — обход шины. После `vm_init`, потому что окно ECAM надо
   сперва отобразить.
6. **`trap_init`**, **`timer_init`** — вектор ловушек и первый `stimecmp`.
7. **Создание задач** и монтирование имён.
8. **`scheduler_start()`** — с этого момента ядро существует только как
   обработчик ловушек.

## 2. Память

### 2.1 Физические страницы — `pmm.c`

Сорок восемь строк. Свободные страницы связаны в список **через самих себя**:
первое слово свободной страницы — указатель на следующую свободную, так что
никаких отдельных метаданных нет.

```c
struct run { struct run *next; };
static struct run *freelist;
```

Приём работает, пока RAM отображена «адрес в адрес» (VA == PA) — именно так
ядро отображает себя.

- `pmm_init()` раздаёт всё от `PGROUNDUP(_end)` до `PMM_TOP`.
- `pmm_free()` **отказывается** от всего, что не является страницей внутри
  арены: невыровненный адрес, адрес ниже `RAM_BASE` или выше `PMM_TOP`
  игнорируется молча.
- `pmm_alloc()` **обнуляет** страницу перед выдачей. Это не вежливость: на
  этом держатся две вещи — таблицы страниц требуют нулей, и `.bss` программы
  берётся именно отсюда (в `vm_load_segment` всё, что за `filesz`, просто
  никогда не записывается).

Арена кончается на `PMM_TOP = 0x83000000`, ниже образа диска на `0x84000000`:
образ FAT16 лежит в памяти и его нельзя раздать как свободные страницы.

### 2.2 Трансляция — `vm.c`

Виртуальный адрес Sv39 — 39 бит, знаково расширенных до 64:

```
[63:39] копия бита 38 │ VPN[2] 9 бит │ VPN[1] 9 бит │ VPN[0] 9 бит │ смещение 12
```

Обход — по дереву из трёх уровней. `satp` содержит номер физической страницы
корневой таблицы; каждая таблица — одна страница 4 КиБ из 512 записей по 8
байт (512 = 2⁹, отсюда и девять бит на индекс).

**Запись таблицы (PTE)**, `src/riscv.h:52`:

| бит | имя | смысл |
|-----|-----|-------|
| 0 | `V` | запись действительна |
| 1 | `R` | чтение |
| 2 | `W` | запись |
| 3 | `X` | исполнение |
| 4 | `U` | доступна из пользовательского режима |
| 5 | `G` | глобальная |
| 6 | `A` | к странице обращались |
| 7 | `D` | страница изменена |

Запись с `R=W=X=0` — **указатель** на следующую таблицу. Любой из этих трёх
битов делает запись **листом**, и обход останавливается. Отсюда суперстраницы:
лист на уровне 1 покрывает 2 МиБ, на уровне 2 — 1 ГиБ. Это не отдельный
механизм, а ранняя остановка того же обхода.

`A` и `D` ставятся сразу при отображении, чтобы никогда не ловить ловушку
«обращение/изменение»; прав они не дают — права по-прежнему в `R/W/X`.

**Функции:**

- `walk(pt, va, alloc, stop_level)` — спуск к записи. Возвращает 0, если путь
  перекрыт суперстраницей.
- `vm_map_at(pt, va, pa, size, perm, level)` — отобразить диапазон
  страницами указанного уровня.
- `vm_create_task_pt()` — новое адресное пространство: образ ядра и MMIO, и
  больше ничего. Ни чужих страниц, ни арены свободных страниц.
- `vm_translate_in(pt, va)` — трансляция в произвольной таблице.
- `vm_copy_across(dpt, dva, spt, sva, len)` — копирование **между** адресными
  пространствами. Работает только пока установлена таблица ядра: именно
  тождественное отображение делает физический адрес пригодным как указатель, и
  это то, что позволяет ядру быть посредником между двумя изолированными
  задачами.
- `vm_unmap_page(pt, va)` — снять страницу и вернуть кадр. Возвращает кадр
  только если `pa != va`: тождественно отображённое разделяется со всеми, и
  освободить его значило бы освободить память ядра.
- `vm_free_task(t)` — обход всего дерева с тем же правилом.
- `vm_load_segment(t, src, seg)` — реализовать один сегмент PT_LOAD в чужом
  пространстве: выделить и отобразить `memsz` байт, скопировать `filesz`,
  остальное оставить нулями.

### 2.3 Карта адресов

**Физическая** (плата QEMU `virt`, `src/riscv.h`):

| адрес | что |
|-------|-----|
| `0x02000000` | CLINT |
| `0x0c000000` | PLIC, 4 МиБ |
| `0x10000000` | UART 16550, прерывание 10 |
| `0x10001000` | virtio-mmio, 8 слотов через 0x1000, прерывания 1..8 |
| `0x30000000` | окно конфигурации PCI (ECAM), 256 МиБ |
| `0x40000000` | окно MMIO для PCI |
| `0x80000000` | начало RAM |
| `0x83000000` | конец арены свободных страниц |
| `0x84000000` | образ FAT16, 8 МиБ |
| `0x88000000` | конец RAM (128 МиБ по умолчанию) |

Ядро отображает RAM суперстраницами по 2 МиБ (64 записи на все 128 МиБ), а
UART — намеренно страницей 4 КиБ, чтобы хотя бы одно отображение проходило
полный трёхуровневый обход: это видно в `cat /proc/pagetable`.

**Виртуальная, в каждой задаче:**

| адрес | что |
|-------|-----|
| `0x20000000` | программа с диска (текст, данные, bss) |
| `0x28000000` | куча; `UHEAP_TOP = 0x2f000000` — потолок |
| `0x30000000` | вершина стека, четыре страницы вниз (16 КиБ) |
| `0x40000000` | окно DMA, по странице на вызов |

Стек каждой задачи — по одному и тому же виртуальному адресу, но на разных
физических страницах. В этом и смысл: у задачи A просто нет отображения для
стека задачи B.

### 2.4 Куча и `sbrk`

Ядро участвует в работе `malloc` ровно одним вызовом и одной страницей.

- При создании задачи ядро отображает **одну** страницу по `UHEAP_BASE` и
  ставит `brk = UHEAP_BASE + 4096`. Страница приходит обнулённой.
- `sbrk(delta)` сдвигает `brk` и возвращает **прежнее** значение. Рост
  отображает свежие кадры, сжатие снимает их и возвращает, после чего
  выполняется `sfence.vma` — задача продолжит работу с тем же `satp`, а
  исчезнувшее отображение может остаться в TLB.
- Если память кончилась на полпути, вызов снимает то, что успел взять:
  неудавшийся `sbrk` оставляет адресное пространство точно таким, каким нашёл.
- Первая страница никогда не возвращается.

Зачем страница при рождении: распределитель (`src/malloc.h`) держит своё
состояние **по фиксированному адресу**, в начале управляемой им области, а не в
переменной. Причина — в 3.5.

## 3. Задачи

### 3.1 `struct task`

Первое поле — `struct context`, и это обязательно: `entry.S` сохраняет
регистры по смещениям от начала структуры.

```c
struct context {
    uint64 x[32];    /* регистры, x[i] по смещению i*8 */
    uint64 epc;      /* смещение 256: где задача продолжится */
    uint64 status;   /* смещение 264: привилегия и прерывания на sret */
    uint64 satp;     /* адресное пространство, ставится на выходе */
};
```

Остальные поля:

| поле | назначение |
|------|-----------|
| `pt` | корневая таблица страниц |
| `state` | `T_UNUSED`, `T_RUNNABLE`, `T_RUNNING`, `T_BLOCKED` |
| `id`, `gen` | идентификатор и поколение слота |
| `name`, `namebuf` | имя; `namebuf` — для имён, пришедших системным вызовом |
| `ns` | пространство имён: что для этой задачи значат пути |
| `send_va`, `send_len` | где лежит сообщение задачи, заблокированной в `send` |
| `recv_va`, `recv_len` | куда хочет получить сообщение заблокированная в `recv` |
| `waiting_recv` | 1 — заблокирована в `recv`, 0 — в `send` |
| `recv_closed`, `recv_from` | закрытый приём: ждёт одного названного отправителя |
| `irq_pending` | устройство сработало, пока драйвер был занят |
| `timer_pending` | будильник сработал, пока задача была занята |
| `dma_next` | следующий свободный адрес в окне DMA |
| `brk` | вершина кучи |
| `alarm_at` | абсолютное время побудки, 0 — нет будильника |
| `wait_for` | ждёт исчезновения этой задачи |
| `wait_sender` | голова очереди отправителей, ждущих **нас** |
| `send_next` | звено в такой очереди, когда в ней стоим мы |

### 3.2 Идентификатор: слот и поколение

```c
#define TASK_SLOT(id)  ((id) & 0xff)
#define TASK_GEN(id)   ((id) >> 8)
```

Номера слота недостаточно, потому что слоты переиспользуются. Всё, что
запомнило «задача 6» — сервер с неотвеченным запросом, запись в таблице
монтирования — продолжало бы в это верить после смерти задачи 6 и заселения
слота кем-то другим.

Поколение делает устаревший идентификатор **именем никого**, а не именем не
того. Разница — между запросом, который провалится, и ответом, доставленным
невинной задаче.

`task_by_id(id)` — единственный правильный способ превратить идентификатор в
задачу: он проверяет и занятость слота, и совпадение поколения. Индексировать
`tasks[]` напрямую — та самая ошибка, ради которой он существует.

### 3.3 Планировщик

Круговой обход `tasks[]`, начиная со следующего за текущим. Выбирается первая
задача в состоянии `T_RUNNABLE`. Приоритетов нет.

Вытеснение — по таймеру, примерно каждые 50 мс (`TICK = 500000` при частоте
10 МГц). Кроме того, `schedule()` вызывается **прямо из системного вызова**,
когда задача блокируется: блокировка — это переключение контекста тут же, на
месте.

Внутри ядра вытеснения нет: обработчик ловушки выполняется до конца.

### 3.4 Три способа создать задачу

| функция | для кого | особенности |
|---------|----------|-------------|
| `task_create(name, entry)` | задача ядра в S-режиме | `sstatus.SPP = 1`, страницы без `PTE_U` |
| `task_create_user(name, entry, data_start, data_end)` | сервер в U-режиме | + общий пользовательский текст, + личный участок данных, `SPP = 0` |
| `task_new_empty(name)` | программа с диска | пустое пространство; сегменты придут через `vmload`, состояние `T_UNUSED` до `start` |

Все три получают стек (4 страницы под `USTACK_TOP`) и страницу кучи.

### 3.5 Общий текст, личные данные

`task_create_user` отображает два диапазона:

- `__utext_start .. __utext_end` — **общий** для всех пользовательских задач,
  `R|X|U`. Все серверы выполняют один и тот же текст, как общую библиотеку.
- `data_start .. data_end` — **личный**, `R|W|U`. Свой у каждого сервера, так
  что один сервер не дотянется до буферов другого, хотя код у них общий.

Границы личных участков задаются в `src/kernel.ld` пофайлово. **Сервер, чей
код не попал в `.utext`, стартует и умирает молча** — это стоило одного
вечера отладки при добавлении `srv_dev.o`.

Из этого же правила следует форма двух других вещей:

- **`spawn` не мог иметь собственного буфера.** Он лежит в общем тексте и
  вызывается оболочкой; статический буфер в `loader.c` был бы по адресу,
  отображённому в задачу загрузчика, а не вызывающего. Отсюда `ELFMAX` —
  буфер передавался вызывающим. Ныне `spawn` выделяет память.
- **Распределитель памяти не имеет ни одной переменной.** По той же причине:
  `static struct mheap *heap` упал бы при первом же `malloc` из оболочки.
  Состояние кучи лежит в начале самой кучи, по фиксированному адресу, а ядро
  отображает эту страницу при рождении задачи — потому что иначе понадобился
  бы системный вызов на каждый `malloc`, только чтобы спросить, есть ли куча.

### 3.6 Нити

Задача была адресным пространством и одной нитью управления. `sys_thread`
разделяет эти два понятия: новая задача получает таблицу страниц вызывающего
вместо своей и отличается от него ровно одним — **собственным сохранённым
контекстом**. Это и есть нить.

```c
t->pt       = current->pt;      /* целиком: то же адресное пространство */
t->ctx.satp = current->ctx.satp;
t->ctx.x[2] = sp;               /* стек назвал вызывающий */
t->ctx.x[10]= arg;              /* entry(arg) */
t->ns       = current->ns;
t->brk      = current->brk;     /* куча одна, значит и граница одна */
```

Ничего в системе не пришлось менять: планировщик, путь ловушек, сообщения и
`/proc` работают с нитью как с задачей, потому что она ею и является. У нити
есть идентификатор, слот и строка в `ps` — иначе она не могла бы участвовать в
обмене сообщениями, а другого способа общения здесь нет.

**Стек даёт вызывающий**, и это не упрощение. Стек всякой задачи лежит по
`USTACK_TOP`, что работает лишь потому, что адресные пространства разные; двум
нитям в одном пространстве он достаться не может. Вызывающий выделяет стек
обычным `malloc` из общей кучи и называет его вершину, а у ядра не остаётся
мнения о том, каким должен быть размер стека.

**Что становится общим, то становится гонкой.** Куча одна на пространство, и
первое, что ломается от появления второй нити, — распределитель памяти.
Поэтому в `src/malloc.h` есть замок: одно атомарное `amoswap` (расширение A
входит в rv64imac), удерживаемое на всю операцию выделения, потому что список
свободного обходится, режется и сшивается как одно действие. Ожидание — с
уступкой процессора, а не с прожиганием кванта: держатель замка это задача, к
которой планировщик обязан вернуться.

Проверить обе стороны можно программой `/BIN/THREADS.ELF`:

```
без замка:  300 из 1200  — потеряно на гонке
с замком:   1200 из 1200  сходится
1600 malloc/free из четырёх нитей: прошло
```

**Первое, ради чего они понадобились**, — несколько сессий telnet сразу.
`srv_rsh.c` держал состояние сессии файловыми статиками и обслуживал одну за
раз; теперь состояние в `struct session`, а на каждое принятое соединение
заводится нить. Проверено девятью одновременными сессиями: каждая отвечает
независимо, вывод программы уходит только в своё соединение, Ctrl-C убивает
только свою программу.

Ключ к этому — что **нити делят память, но не обязаны делить смысл имён**.
Пространство имён это поле задачи, а не адресного пространства, поэтому нить
сессии зовёт `sys_nsclone()` для себя и привязывает `/dev/console` к своему
соединению; порождённые ею программы наследуют её пространство, а не соседкино.

И ошибка, которую это немедленно нашло: **соединение должна открывать та задача,
которая его закроет.** Держателя соединение помнит по идентификатору задачи, а
нить — отдельная задача; открыть в родителе и закрыть в нити значит добавить
ссылку одному и снять у другого, счётчик не доходит до нуля, и соединение
навсегда остаётся в `close-wait`. Три висящих соединения при пяти вошедших и
вышедших — так это и выглядело.

Что **не** сделано: нить, умершая с замком в руках, вешает распределитель для
всех остальных нитей своей задачи. Это верно про всякий замок во всякой
системе и здесь не исправлено.

### 3.7 `task_retire` — что чинится при смерти задачи

Пять действий, и каждое закрывает свою дыру:

1. **Отправители, ждавшие эту задачу**, будятся с −1: их `send` проваливается,
   а не висит вечно.
2. **Задача снимается с чужой очереди отправителей.** Нигде не записано, кому
   она отправляла, поэтому просматриваются очереди всех задач. Без этого
   остаётся указатель на освобождённую задачу, по которому пойдёт следующий
   приём. Дыра была недостижима, пока не появился `kill`: заблокированная в
   `send` задача не выполняется и потому не могла дать сбой.
3. **Ждущие в `wait`** будятся нулём — они ждали ровно этого.
4. **Ждущие в закрытом приёме именно от неё** будятся с −1: это единственное
   ожидание, которое можно направить на задачу, которая затем исчезает.
5. **Страницы возвращаются** (`vm_free_task`), поколение слота увеличивается,
   и вызывается сборка мусора пространств имён — это единственный момент,
   когда пространство может стать ничьим.

Пятый пункт с появлением нитей стал сложнее: адресное пространство уходит
только если в нём никто больше не стоит. Проверяется просмотром таблицы задач —
по той же причине, по которой сборка пространств имён сделана просмотром, а не
счётчиком ссылок. Первая же нить, умершая без этой проверки, вынула бы память
из-под остальных, включая стек, на котором стоит та, что выполняет
освобождение.

**И слот при выдаче обнуляется целиком, кроме поколения.** `task_retire`
чистит то, что опасно *в тот момент* — очередь отправителей, флаги приёма, — а
десяток других полей просто оставался: `wait_for`, `alarm_at`, `recv_closed`,
`irq_pending`, `dma_next`. Каждый путь создания задачи до сих пор случайно
выставлял те поля, которые его волновали, что не то же самое, что их
правильность. Нити сделали разницу видимой, переиспользуя слоты по четыре
разом: машина вставала целиком.

Ровно то же самое делает сбой в MMU: `kill` и страничный сбой — один и тот же
путь.

## 4. Ловушки и прерывания

### 4.1 Вход — `entry.S`

Пока задача выполняется, `sscratch` содержит `&current->ctx`.

```asm
_strap:
    csrrw   t6, sscratch, t6     # t6 = &ctx, sscratch = прежний t6
    sd      x1,  8(t6)           # сохранить все регистры по смещениям
    ...
```

Дальше сохраняются `sepc` и `sstatus`, ставится таблица ядра, происходит
переход на **личный стек ловушек** и вызывается `strap_handler()`. Обработчик
может выбрать другую `current`; на выходе восстанавливается — возможно, уже
другой — контекст, и выполняется `sret`.

Стек пользователя для этого не годится: он может быть невалиден, полон, или
принадлежать задаче, которую мы как раз снимаем.

Вектор был `mscratch/mepc/mstatus/mret`, пока не появилась страничная память:
`satp` в M-режиме игнорируется, поэтому включение Sv39 означало перенос ядра в
S-режим вместе со всем путём обработки ловушек.

### 4.2 Разбор — `trap.c`

```c
if (scause & CAUSE_INT) {
    таймер   → перезарядить, проверить будильники, schedule()
    внешнее  → device_interrupt()
} else if (ecall) {
    epc += 4;  syscall_dispatch(a7);
} else {
    сбой: напечатать и снять задачу
}
```

`epc += 4` до диспетчеризации: задача должна продолжиться **за** инструкцией
`ecall`, а не выполнить её снова.

Сбой не роняет ядро. Он печатается и снимает виновную задачу — благодаря
этому демонстрация при загрузке может намеренно писать в страницу только для
чтения и остаться в живых, чтобы об этом рассказать.

### 4.3 Таймер

Sstc: CSR `stimecmp`, включённый через `menvcfg.STCE` в M-режиме. `TICK =
500000`, база времени QEMU — 10 МГц, то есть вытеснение примерно каждые 50 мс.

Будильники (`alarms_check`) проверяются на каждом тике. Разбудить задачу
выглядит **в точности** как доставить ей сообщение — задача, стоящая в `recv`,
получает `TIMER_SENDER` в `a0`. Именно это позволяет одному блокирующему
вызову обслуживать сообщения, прерывания и таймауты одинаково.

### 4.4 Прерывания устройств

`plic.c`: контроллер PLIC, claim/complete. Владельцы записаны в
`irq_owner[NIRQ]`, `NIRQ = 32`.

```
устройство → PLIC → ядро: claim
                    ↓
       владелец в recv?  да → recv возвращает IRQ_SENDER (−2)
                         нет → irq_pending = 1, увидит на следующем recv
                    ↓
       источник остаётся замаскированным, пока драйвер не сделает irq_ack
```

**Ядро намеренно не трогает устройство.** Оно не знает как. Оно снимает
заявку с PLIC, сообщает владельцу и оставляет линию замаскированной — это и
есть противодавление, не дающее шторму прерываний захлестнуть
пользовательский драйвер, пока тот ждёт планировщика.

Если владельца нет, прерывание завершается (`plic_complete`), чтобы линия
замолчала: делать с данными всё равно нечего.

## 5. Обмен сообщениями

Двести тринадцать строк в `src/ipc.c` — и это весь IPC системы. Другого нет.

### 5.1 Рандеву

`send(dst, buf, len)` блокируется, пока `dst` не примет. `recv(buf, cap)`
блокируется, пока кто-нибудь не пошлёт.

**Очереди сообщений нет.** Есть очередь **отправителей** — односвязный список,
вшитый в сами задачи (`wait_sender` у получателя, `send_next` у стоящих в
очереди). Сообщение всё это время лежит в памяти отправителя нетронутым.

### 5.2 Копирование

```c
static int deliver(struct task *snd, uint64 sva, int slen,
                   struct task *rcv, uint64 rva, int rlen)
{
    int n = slen < rlen ? slen : rlen;      /* обрезать по тому, что примут */
    return vm_copy_across(rcv->pt, rva, snd->pt, sva, n) < 0 ? -1 : n;
}
```

У каждой задачи своя таблица страниц, поэтому адрес отправителя в пространстве
получателя не значит ничего. Отсюда форма файлового протокола: `struct vfs_req`
носит данные **внутри себя**, а не указателем.

Сообщение обрезается по тому, что получатель готов принять, — молча.

### 5.3 Четыре точки входа

| вызов | поведение |
|-------|-----------|
| `send` | ждёт, если получатель не готов |
| `trysend` | −1 вместо ожидания |
| `recv` | принимает от кого угодно |
| `recvfrom` | принимает только от названного |

**`trysend` появился не для удобства.** Рандеву заклинивает в тот момент,
когда две задачи решают послать друг другу: каждая паркуется в очереди другой,
и до `recv` не доходит ни одна. Все задачи обходили это случайно, пока не
появился прокси, который держит припаркованное чтение из сети и одновременно
в неё пишет. Сервер, отвечающий на отложенный запрос, обязан уметь **не
смочь**: он единственный, кто знает, что клиент может быть занят.

**Закрытый приём — исправление ошибки, а не оптимизация.** Ответ не является
событием: клиент, пославший запрос, точно знает, кто ему должен, и взять
следующее сообщение от кого попало — не гонка, а ответ на другой вопрос.
Поэтому `dequeue_sender` умеет вынимать из середины очереди: чужое остаётся
стоять, где стояло.

```c
static int wants(struct task *dst, struct task *src)
{
    if (dst->state != T_BLOCKED || !dst->waiting_recv) return 0;
    return !dst->recv_closed || dst->recv_from == src->id;
}
```

Задача в закрытом приёме заблокирована, но **недоступна** тому, кого не
назвала.

### 5.4 Псевдоотправители

`recv` возвращает идентификатор отправителя, либо:

- `IRQ_SENDER = −2` — сработало устройство, которым владеет эта задача;
- `TIMER_SENDER = −3` — истёк будильник.

Прерывание обгоняет очередь сообщений при открытом приёме: устройство
замаскировано до подтверждения. Флаги залипающие, и **закрытый приём их не
трогает** — их подберёт следующий открытый.

### 5.5 Отказы

- Отправка по идентификатору, который никого не называет (пустой слот или
  устаревшее поколение), проваливается, а не блокируется и не доставляется
  тому, кто занял слот.
- **Отправка самому себе отвергается.** Рандеву нужны двое; задача,
  пославшая себе, встала бы в собственную очередь и никогда не дошла бы до
  `recv`, чтобы снять оттуда сообщение. А поскольку такая задача обычно
  сервер, вместе с ней встало бы всё, что её о чём-то спрашивало. Проверка —
  одно сравнение на каждое сообщение.

### 5.6 Цена

- `struct vfs_req` — **664 байта** (4 + 4 + 128 + 4 + 8 + 4 + 512).
- Круг «запрос-ответ» через сервер — **110–120 мкс**: два системных вызова,
  две копии по 664 байта, два переключения контекста. Измеряется командой
  `ping /`.
- Отсюда все решения об экономии сообщений в надстройке: `curses` шлёт только
  разницу, загрузчик читает файл целиком, `mc` строит экран в буфере.

## 6. Пространство имён

Модель Plan 9: у каждой задачи своя таблица, путь разрешается **дважды** — в
задачу-сервер и в имя, о котором её надо спросить.

### 6.1 Структуры

```c
struct mount {
    char prefix[16];         /* имя, за которое отвечают */
    int  kind;               /* MNT_SERVER или MNT_BIND */
    int  server;             /* MNT_SERVER: кто отвечает */
    char target[128];        /* MNT_BIND: имя, которое это значит */
};

struct namespace {
    struct mount mnt[8];
    int n, used;
};
static struct namespace ns_pool[8];   /* ns_pool[0] — корневое */
```

Восемь пространств, по восемь записей. Наследование: новая задача получает
пространство родителя (`t->ns = current->ns`) — то есть **видит то же, что и
родитель**. Это существенно: оболочка привязывает `/dev/console` к соединению,
и запущенная ею программа пишет в соединение, не зная об этом.

`vfs_ns_clone()` даёт личную копию (снимок), после которой можно расходиться.

**Сборка мусора — просмотром, а не счётчиком ссылок.** Счётчик должен быть
верен в каждом месте, где копируется указатель на пространство; один
пропущенный инкремент — либо слот, который никогда не вернётся, либо, хуже,
освобождённый при живом владельце. Просмотр должен быть верен один раз.
Вызывается при снятии задачи — единственный момент, когда пространство может
стать ничьим. «Живая» здесь значит то же, что и в `alloc_slot`: задача в
процессе создания имеет `T_UNUSED` и таблицу страниц, и её пространство очень
даже занято.

### 6.2 Две операции, и они разные

- **`mount(prefix, task, flags)`** — поставить сервер за имя.
- **`bind(old, new, flags)`** — сделать так, чтобы `new` значило `old`.
  Порядок аргументов — как в Plan 9, и его все путают: меняется **второй**.

Флаги: `MREPL` (заменить), `MBEFORE`, `MAFTER` (присоединить — тогда у имени
несколько ответов, то есть объединение).

Порядок записей в таблице ничего не значил ровно до появления объединений.
С ними порядок — это порядок перебора, поэтому `unmount` **сдвигает** записи,
а не переставляет последнюю на освободившееся место: перестановка молча
переупорядочила бы объединение.

### 6.3 Разрешение имени

```c
int vfs_resolve(const char *path, char *out, int cap, int nth);
```

Возвращает идентификатор задачи-сервера и записывает в `out` имя, о котором её
надо спросить. Это разные вопросы, как только в деле есть привязка:
`/dev/console` может быть соединением, а сервер на том конце про такое имя
никогда не слышал.

**Правило совпадения** (`prefix_matches`): префикс должен кончаться там, где
кончается компонент пути, иначе `/mnt` захватил бы `/mnt2/x` и переписал бы
его в `2/x`. Префикс с косой чертой на конце (`/dev/`, `/`) кончается на
границе по построению; кроме того, такой префикс совпадает и с именем **без**
косой черты — `/proc` это то, что набирает человек.

**Самое длинное совпадение** решает, какое имя сработало; все записи с этим
же именем — члены объединения, перебираемые в порядке таблицы. Отсюда
уживаются два сервера под `/dev`: консоль смонтирована на точное имя
`/dev/console`, сервер устройств — на префикс `/dev/`.

**Привязки разрешаются циклом**, не более `RESOLVE_HOPS = 4` шагов; больше —
значит петля, и ответ −1. Выбор члена объединения делается **один раз**, на
имени, которое спросил вызывающий: вложенные объединения — общность, которая
здесь не нужна и которую не удалось бы объяснить.

## 7. Файловый протокол

### 7.1 Запрос

```c
struct vfs_req {
    int    op;                  /* операция */
    int    fd;                  /* дескриптор на стороне сервера */
    char   path[128];           /* для open */
    int    len;                 /* сколько байт просят или дают */
    unsigned long ioctl_cmd;
    int    result;              /* ответ: байты, дескриптор, размер или −1 */
    char   data[512];           /* данные, в обе стороны */
};
```

Данные **внутри** запроса, а не указателем: указатель на другой стороне ничего
не значит. Отсюда же чтение порциями по 512 байт — цена изоляции, сделанная
видимой.

### 7.2 Операции

`VFS_OPEN`, `VFS_CREATE`, `VFS_READ`, `VFS_WRITE`, `VFS_IOCTL`, `VFS_CLOSE`.

### 7.3 Ioctl'ы

| команда | о чём | соглашение |
|---------|-------|-----------|
| `GETSIZE` | об открытом файле | размер в `result` |
| `REMOVE` | об открытом файле | удалить, не записывая обратно |
| `MKDIR` | о пути, не о дескрипторе | создавать ещё нечего открывать |
| `PING` | **о сервере** | отвечается до того, как посмотрят на `fd` |
| `INTR` | о терминале | `len` = задача, которую убить при символе прерывания; 0 снимает назначение и отвечает, сработало ли. Реализован **дважды** — см. ниже |
| `DOC` | о сервере | `len` = **смещение**, ответ в `data`, 0 — конец |
| `CONF` | о сервере | так же, но числа, с которыми он собран |
| `HOLDS` | о сервере | `len` = **идентификатор задачи**, одним сообщением |

Два разных смысла у поля `len` — то, что эта схема может себе позволить один
раз на поле. Первая версия `HOLDS` отвечала через листающий помощник, и
сетевой сервер принял номер задачи 13 за смещение, срезав ровно тринадцать
символов с начала ответа. Поэтому помощников два, и имя каждого говорит, какой
это случай.

### 7.4 Дисциплина линии — отдельный сервер

Символ прерывания должен заметить тот, кто видит байты первым, а первым их
видит владелец источника. Поэтому `INTR` был написан **дважды**, в консольном
и в сетевом сервере, и успел разойтись: сетевая версия убивала задачу и клала
байт в очередь всё равно, так что на одно нажатие печаталось два `^C`.

Теперь между драйвером и читающей программой стоит `srv_tty.c`, и всё, что
раньше разбирал каждый читатель сам, разбирается один раз:

```
/tty/ctl        write "new /net/tcp/0"  -> "ok 3"
/tty/3          read  — готовая строка; write — насквозь в устройство
```

Дальше `bind /tty/3 /dev/console`, и программа получает варёный ввод, ничего
об этом не зная. Она же может от него отказаться — привязав `/dev/console`
прямо к устройству, — и **это выбор того, кто её запускает**, а не её
собственный. Ровно поэтому дисциплина сделана сервером, а не библиотекой.

`IOCTL_TTYMODE` переключает сырой режим: байты как пришли, без эха и без
правки строки — за одним исключением. За возвратом каретки отбрасывается
следующий за ним NUL или перевод строки: RFC 854 велит слать Enter как CR NUL,
а клиент в строчном режиме шлёт CR LF, и это одно нажатие. Программа,
считающая и 13, и 10 за Enter, права; знание о том, что устройство шлёт их
парой, принадлежит терминалу. Без этого `mc` на каждый Enter заходил в каталог
и тут же выходил обратно. Это то, что значит `cbreak()` в `curses.h`, и он его и зовёт —
вместе с telnet-переговорами, потому что дальний конец может быть и тем и
другим.

**Сервер не может блокироваться в чтении чужого сервера** — он перестанет
отвечать всем остальным. Поэтому у каждой линии своя нить: она стоит в
`vfs_read` на устройстве, прогоняет дисциплину и, когда строка готова, будит
главный цикл. Отвечает отложенному клиенту **главный цикл**, а не нить: клиент
ждёт в закрытом приёме, который называет задачу, которой он послал. Ответ от
нити остался бы в очереди навсегда.

Первая попытка сделать такой сервер была откачена именно здесь — нитей тогда
не существовало, и это была не ошибка реализации, а отсутствие механизма.

### 7.5 Дескриптор

```c
return (srv << 16) | (r.result & 0xffff);
```

Верхняя половина — идентификатор задачи-сервера, нижняя — дескриптор внутри
этого сервера. **Клиентской таблицы дескрипторов не существует**: дескриптор
сам является маршрутом, и после открытия ни имя, ни таблица монтирования
больше не нужны.

Следствие, которое приходится принимать: узнать, что у задачи открыто, можно
только спросив каждый сервер (см. `/proc/<id>/fd`).

## 8. Справочник системных вызовов

Все тридцать. Номер в `a7`, аргументы в `a0`–`a3`, ответ в `a0`.
Определения — `src/syscall.h`, диспетчер — `syscall_dispatch` в `src/task.c`
и `ipc_syscall` в `src/ipc.c`.

### Планирование и время

**0 · `yield()`** — отдать остаток кванта. Не блокирует.

**18 · `alarm(ms)`** — разбудить через `ms` миллисекунд; 0 отменяет.
Единственный способ для задачи действовать по прошествии времени. Побудка
приходит как `TIMER_SENDER` в `recv`. Будильник **один** на задачу.

**23 · `wait(task)`** — блокироваться, пока названная задача не исчезнет.
Возвращает 0. Заменил опрос через `alive`, который сжигал квант на проверку.

**26 · `kill(task)`** — снять задачу. Ровно то же, что делает с ней сбой.
Самой задаче не доставляется ничего: сигналов здесь нет. Нельзя убить себя
(для этого `exit`) и **слот 0** — это та задача, которая была создана первой,
то есть при загрузке файловая система: машина, которая не может открыть файл,
не может и загрузить программу, чтобы себя починить. Задача `idle` при этом
не защищена: `schedule()` уходит в `wfi`, если готовых нет, так что её
убийство стоит машины, которая простаивает в останове, а не в цикле. Без
всякой охраны.

**28 · `self()`** — свой идентификатор. Понадобился, когда серверу пришлось
узнавать себя в списке серверов.

**29 · `thread(entry, sp, arg)`** → идентификатор новой нити. Задача, которой
отдана таблица страниц вызывающего, а не своя; общими становятся память, куча
и пространство имён. Стек называет вызывающий: у ядра нет мнения о его
размере. Единственный вызов, который создаёт задачу **без** адресного
пространства.

**14 · `exit()`** — не возвращается.

### Сообщения

**1 · `send(dst, buf, len)`** — блокируется, пока `dst` не примет. −1, если
такой задачи нет или это мы сами.

**22 · `trysend(dst, buf, len)`** — −1 вместо блокировки. То, чем сервер
отвечает на отложенный запрос: ждать клиента он не имеет права.

**2 · `recv(buf, cap)`** → идентификатор отправителя, либо −2 (прерывание),
либо −3 (таймер).

**24 · `recvfrom(src, buf, cap)`** → `src`, либо −1, если та задача уже
исчезла или исчезнет за время ожидания. Сообщения от других остаются в
очереди.

### Имена

**20 · `mount(prefix, task, flags)`** — поставить сервер за имя.
**9 · `bind(old, new, flags)`** — `new` теперь значит `old`.
**21 · `unmount(name)`** — забрать имя целиком, со всем объединением.
**10 · `nsclone()`** — личная копия пространства имён.
**5 · `resolve(path, out, cap, nth)`** → кто отвечает и о каком имени
спрашивать; `nth` выбирает члена объединения, −1 если такого нет.
**7 · `mounts(task, out, cap)`** → таблица задачи текстом; `task < 0` — своя.

### Память

**25 · `sbrk(delta)`** → прежняя граница кучи. Весь вклад ядра в наличие
распределителя памяти.

**17 · `dma_alloc(out)`** — одна обнулённая страница в окне DMA, сообщается
**обоими** адресами, виртуальным и физическим. Единственное место, где
программе законно нужен физический адрес: устройство читает память по нему.

**8 · `meminfo(int[2])`** → свободные и всего страниц.

### Запуск программы

**11 · `newtask(name)`** → идентификатор пустого адресного пространства.
**12 · `vmload(id, seg)`** — один сегмент PT_LOAD в страницы.
**13 · `start(id, info)`** — точка входа, и пусть выполняется.

Три примитива подобраны под то, что и так написано в заголовке программы ELF,
поэтому загрузчик живёт в пользовательском режиме, а ядро не обязано знать,
что такое ELF. **Сознательно без охраны**: любая задача может построить
другую.

### Устройства

**15 · `irq_register(irq)`** — эта задача становится драйвером устройства.
**16 · `irq_ack(irq)`** — обработано, можно срабатывать снова (снимает маску).
**27 · `devinfo(what, n, out, cap)`** — дерево устройств, шина PCI или
описание самого ядра.

### Наблюдение

**6 · `taskinfo(index, out)`** — одна задача **по индексу слота**, не по
идентификатору: имя, состояние, чего ждёт, сколько отправителей в очереди.
**19 · `alive(task)`** — тот ли это ещё, кем был. Отвечает «нет» и для пустого
слота, и для переиспользованного.
**4 · `pgdump(task, va, out, cap)`** — одна трансляция, пройденная и
отрисованная. Только ядро может это сделать: оно единственное работает с
таблицей, через которую видны сами таблицы страниц.
**3 · `putc(c)`** — консоль в обход сервера. Для журнала загрузки и для
случая, когда сервера, который бы рассказал, уже нет.

## 9. Серверы образа

Ядром не являются: выполняются в U-режиме. Перечислены в порядке создания в
`kmain.c`; номер — идентификатор задачи при загрузке.

| № | имя | исходник | отвечает за | что это |
|---|-----|----------|-------------|---------|
| 0 | `fs` | `srv_fs.c`, `fat16.c`, `srv_blk.c` | `/` | FAT16 на virtio-blk, целый файл в буфере |
| 1 | `console` | `srv_console.c` | `/dev/console` | UART, драйвер в пользовательском режиме |
| 2 | `proc` | `srv_proc.c` | `/proc/` | состояние ядра файлами |
| 3 | `null` | `srv_null.c` | — | мусорная корзина, для песочницы |
| 9 | `loader` | `loader.c` | — | `spawn`: чтение ELF и три примитива |
| 10 | `sh` | `sh.c` | — | оболочка на последовательной консоли |
| 11 | `net` | `srv_net.c`, `net_ip.c` | `/net/` | ARP, IPv4, ICMP, UDP, DNS, TCP |
| 12 | `idle` | `kmain.c` | — | всегда готова; без неё `schedule()` уходил бы в `wfi` |
| 13 | `rsh` | `srv_rsh.c` | — | оболочка поверх TCP, порт 23 |
| 14, 15 | `bench`, `pong` | `bench.c` | — | измерение стоимости сообщения |
| 16 | `dev` | `srv_dev.c` | `/dev/`, `/doc/` | дерево устройств, PCI, документация серверов |
| 17 | `tty` | `srv_tty.c` | `/tty/` | дисциплина линии: эхо, правка строки, `^C`, `^D`, telnet |

Слоты 4–8 занимают демонстрации, показывающие изоляцию: `shell` (задача
S-режима), `sandbox` (клонирует пространство имён и отбирает у себя консоль),
`snooper`, `user`, `peeker` — три последние намеренно тянутся к чужой памяти и
снимаются MMU, о чём в журнале загрузки остаётся запись.

Идентификатор задачи — это номер слота при поколении 0, а слоты раздаются в
порядке создания: отсюда числа в первой колонке.

Внутри машины каждый сервер описывает себя сам: `cat /doc/net`, `cat /doc/fs`
и так далее. Это не файлы на диске — это ответ сервера на `IOCTL_DOC`.

## 11. Чего нет

- **Сигналов.** `kill` ничего не доставляет, он просто снимает задачу.
  Прерывание с клавиатуры реализовано иначе: терминалу называют задачу, и он
  её убивает.
- **Прав доступа.** Нигде, ни на чём. Ни у файлов, ни у системных вызовов, ни
  у `/proc/<id>/ctl`.
- **Дисциплины линии в ядре.** Она есть, но снаружи: сервер `/tty/`, который
  включают в путь привязкой имени. Ядро про терминалы по-прежнему не знает
  ничего.
- **Нити, которая не была бы задачей.** Нити есть (`sys_thread`), но у каждой
  свой идентификатор, слот и строка в `ps` — иначе с ней нельзя было бы
  обменяться сообщением, а другого способа общения нет. Ни примитивов
  синхронизации, ни локальной памяти нити ядро не предоставляет: замок — это
  `amoswap` в пользовательском коде.
- **Приоритетов.** Круговой обход по готовым, вытеснение по таймеру.
- **`seek`.** Файл читается вперёд; сервер держит позицию сам. Отсюда модель
  «весь файл в одном буфере».
- **Разделяемой памяти между задачами.** Единственное общее — доступный
  только на чтение общий пользовательский текст. Всё остальное копируется.
- **Вытеснения внутри ядра.** Обработчик ловушки идёт до конца.
- **Многоядерности.** Вторичные харты паркуются в `wfi` при загрузке; поэтому
  во всём ядре нет ни одного замка.

## 12. Известные дыры

Не «планы на будущее», а то, что не сделано и известно, что не сделано.

- **`rsh` не имеет аутентификации никакой.** Кто дотянулся до порта — получил
  оболочку. То же у `exportfs`, который отдаёт пространство имён наружу и
  разрешает запись. Приватность обеспечивается исключительно тем, на каком
  адресе слушает проброс портов (`HOSTIP` в `Makefile`, по умолчанию
  `127.0.0.1`).
- **`newtask`, `vmload`, `start` без охраны.** Любая задача может построить
  другую. Настоящие системы ставят перед этими тремя capability. Разбор того,
  как это можно исправить именами в пространстве имён, отложен.
- **Одна сессия у `rsh`.** Второе соединение принимается на уровне TCP и не
  обслуживается, пока не закончится первое.
- **`/proc/<id>/ctl` принимает `kill` от кого угодно.**
- **Порт 23 на хосте** требует привилегии, которая выдана вне репозитория:
  `setcap cap_net_bind_service` на бинарнике QEMU. Это настройка стенда, а не
  часть системы.
- **Описание ядра в `/doc/kernel` — константа.** Оно может разойтись с кодом
  ровно так же, как комментарий. Серверы описывают себя, **отвечая**, и у них
  такой возможности разойтись нет; у ядра её нет, потому что сам акт
  спрашивания и есть то, что описывается.
